</p>

## Overview
This repository hosts the code for the Dingo Quadruped, a robot designed to be low-cost but capable of conducting research and being extensively modified with additional actuators and sensors. CAD for the Dingo can be found [here](https://github.com/Yerbert/DingoCAD). A full Bill of materials for purchasable components can be found within this repo.

This code is based on the [Stanford Pupper](https://github.com/stanfordroboticsclub/StanfordQuadruped) and [notspot](https://github.com/lnotspotl/notspot_sim_py) codebases, with extensive modifications. It was written for ROS 1 Noetic on a Raspberry Pi and has been **ported to ROS 2 Humble on Ubuntu 22.04**, running on an ELTAY RM66 computer module (Rockchip RK3566) on an ELTAY BB CM4 baseboard.

The repository includes a driver node, `dingo_driver`, which should be used anytime the code is run. It enables joystick control of the Dingo, and allows joint and/or task space commands generated by any other code to be passed through the driver via the appropriate ROS command topics. The joystick can also be toggled on and off to override commands received via ROS command topics.

The repo also includes a Gazebo simulation of the Dingo, based on a URDF file and meshes which are also provided.

## 1. What you need

| Part | Notes |
|---|---|
| Computer | ELTAY RM66 module on the ELTAY BB CM4 baseboard (an Orange Pi CM4 module also fits, according to the baseboard datasheet) |
| Dingo PCB, battery and wiring | see the wiring diagrams in this repo; 4S LiPo battery |
| Servo board and servos | PCA9685 board with 12 servos, on I2C |
| IMU (optional) | BNO055, on I2C |
| Arduino Nano V3 + USB cable | measures battery and servo voltage, detects the e-stop |
| LCD | Waveshare 1.47 inch LCD (172x320), on SPI |
| Gamepad | PS4-type Bluetooth controller (or the keyboard) |
| Development machine (optional) | any computer; Ubuntu 22.04 natively, or Docker on other systems (section 8) |

**Before you power the baseboard for the first time** (from its datasheet):
- the baseboard is either the version with the 3.5 mm audio jack or the version with the 2-pin power connector XP10 (7-27 V). The polarity of XP10 is not written in the datasheet, check the silkscreen and do not guess;
- the GPIO header works at 3.3 V when resistor R78 is fitted and at 1.8 V when R77 is fitted. Find out which one your board has before connecting the Dingo PCB;
- the first power-up is best done from a lab power supply with a current limit, or from a 5 V USB-C supply.

## 2. Project structure and how the driver works

The following flow diagram shows a simplified overview of how a joystick command is handled by the driver to affect joint movements:
<p align="center">
    <img src="assets/Dingo_driver flow diagram.png" style="align:centre" width="50%">
</p>

```.
├── assets                                    Images used in the readme file
├── dingo_nano                                Code for the Arduino Nano V3 to read sensor data and send it to the computer over serial
└── dingo_ws                                  ROS workspace containing all required packages
   └── src
     ├── dingo                                Package containing the driver node and launch files for running the robot
     ├── dingo_control                        Package containing all files related to control, including kinematics and default trot controller
     ├── dingo_description                    Package containing the robot model (URDF file, meshes, rviz configuration)
     ├── dingo_gazebo                         Package containing the Gazebo simulation (Gazebo Classic with ros2_control)
     ├── dingo_msgs                           Package containing the custom messages (JointSpace, TaskSpace, Angle, ElectricalMeasurements)
     ├── dingo_hardware_interfacing
     |  ├── dingo_input_interfacing           Package containing files for receiving and interpreting commands (From a joystick or keyboard)
     |  ├── dingo_peripheral_interfacing      Package containing the Arduino bridge, battery monitor, LCD and IMU code
     |  └── dingo_servo_interfacing           Package containing the hardware interface for sending joint angles to the servo motors
     └── dingo_utilities                      Package containing useful utilities
```

The driver runs a 50 Hz loop in one of three modes:
- **manual** - the joystick (or keyboard) drives the robot. This is the mode after start-up;
- **external** - entered and left with the L1 button. The robot stands still and accepts commands on `/joint_space_cmd` and `/task_space_cmd`;
- **e-stopped** - while `/emergency_stop_status` is true nothing is commanded. When it is released the robot returns to manual mode.

## 3. Install on the robot

### 3.1 Install Ubuntu 22.04 on the RM66

ROS 2 Humble is built for **Ubuntu 22.04 (jammy)**, on both `amd64` and `arm64`. The RM66 is an `arm64` (aarch64) module, so it needs an **Ubuntu 22.04 arm64 image made for this module**. A Raspberry Pi image will not boot on it.

1. Get the Ubuntu 22.04 image for the ELTAY RM66 from ELTAY. The baseboard datasheet states that the Orange Pi CM4 module is fully compatible, so the official Ubuntu 22.04 image of the Orange Pi CM4 is the other candidate. Check that it is Ubuntu 22.04 (not 20.04 or 24.04) and that it enables I2C, SPI and the GPIO chips (see 4.2).
2. Flash it as the vendor describes. According to the baseboard datasheet it has a microSD socket and three buttons: BOOT (puts the module storage into Maskrom mode, used to flash the eMMC), RECOVERY (Recovery mode) and RESET.
3. Boot it, create your user and set up the network (11.1 has the Wi-Fi example for netplan).
4. Update, then check the system:
```bash
sudo apt update && sudo apt upgrade -y
lsb_release -d      # must say Ubuntu 22.04.x LTS
uname -m            # must say aarch64
python3 --version   # must say 3.10.x
```

### 3.2 Install ROS 2 Humble
These are the steps of the official [ROS 2 Humble installation guide](https://docs.ros.org/en/humble/Installation/Ubuntu-Install-Debs.html). If a command fails, check that page, the repository set-up changes from time to time.

Set the locale:
```bash
sudo apt update && sudo apt install locales
sudo locale-gen en_US en_US.UTF-8
sudo update-locale LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8
export LANG=en_US.UTF-8
```
Add the ROS 2 repository:
```bash
sudo apt install software-properties-common
sudo add-apt-repository universe
sudo apt update && sudo apt install curl -y
export ROS_APT_SOURCE_VERSION=$(curl -s https://api.github.com/repos/ros-infrastructure/ros-apt-source/releases/latest | grep -F "tag_name" | awk -F'"' '{print $4}')
curl -L -o /tmp/ros2-apt-source.deb "https://github.com/ros-infrastructure/ros-apt-source/releases/download/${ROS_APT_SOURCE_VERSION}/ros2-apt-source_${ROS_APT_SOURCE_VERSION}.$(. /etc/os-release && echo ${UBUNTU_CODENAME:-${VERSION_CODENAME}})_all.deb"
sudo dpkg -i /tmp/ros2-apt-source.deb
sudo apt update && sudo apt upgrade -y
```
Install ROS 2. On the robot the bare-bones variant is enough (no GUI tools); on a development machine take the desktop variant:
```bash
sudo apt install -y ros-humble-ros-base ros-dev-tools        # on the robot
# sudo apt install -y ros-humble-desktop ros-dev-tools       # on a development machine
```
Load ROS in every new terminal, and use the Cyclone DDS middleware (more robust over Wi-Fi than the default):
```bash
echo "source /opt/ros/humble/setup.bash" >> ~/.bashrc
echo "export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp" >> ~/.bashrc
source ~/.bashrc
ros2 --help        # prints the usage: ROS 2 works
```
If you want to look at the robot from another computer on the same network (for example rviz2), give both computers the same `ROS_DOMAIN_ID`, for example `export ROS_DOMAIN_ID=42`.

### 3.3 Install the dependencies
```bash
sudo apt install -y git build-essential python3-dev python3-pip \
    i2c-tools libi2c-dev python3-smbus gpiod python3-libgpiod \
    python3-evdev python3-serial python3-pil python3-transforms3d \
    ros-humble-rmw-cyclonedds-cpp ros-humble-joy
pip3 install spidev adafruit-circuitpython-servokit adafruit-circuitpython-bno055
```
`spidev` and the Adafruit libraries (which bring in Adafruit Blinka) are not available through rosdep, that is why they come from pip. Do **not** run `rosdep install` for the whole workspace on the robot: it would also install Gazebo and rviz, which the robot does not need (use it on a development machine, section 8). The simulation and the model viewer need more packages, see section 7.

### 3.4 Get the code and build it
```bash
cd ~
git clone -b ros2 https://github.com/DravenL9/DingoQuadruped.git
cd ~/DingoQuadruped/dingo_ws
colcon build --symlink-install
source install/setup.bash
```
The build takes a minute or two on the robot and ends with `Summary: 9 packages finished` (the simulation packages only install files, Gazebo is not needed to build them). Load the workspace in every new terminal:
```bash
echo "source ~/DingoQuadruped/dingo_ws/install/setup.bash" >> ~/.bashrc
source ~/.bashrc
```
After you change the code you only need to run `colcon build --symlink-install` again (Python files are linked, so many changes need no rebuild at all).

## 4. Set up the hardware

### 4.1 Pins (ELTAY BB CM4)
The 40-pin header of the baseboard has the same physical layout as the Raspberry Pi header, so the Dingo PCB keeps its place on the same header positions. The table uses the pin names of the baseboard datasheet (Rockchip names `GPIOx_yn`).

| Function | Header pin | Pin on the ELTAY BB CM4 | Used by |
|---|---|---|---|
| I2C SDA / SCL (PCA9685 servo board, BNO055 IMU) | 3 / 5 | I2C2 (GPIO4_B4 / GPIO4_B5), 2.2 kOhm pull-ups on the board | Adafruit Blinka, `/dev/i2c-2` |
| SPI MOSI / MISO / CLK / CS0 (LCD) | 19 / 21 / 23 / 24 | SPI3, `/dev/spidev3.0` | `dingo_lcd_interfacing.py` |
| LCD RST (BCM 27 on a Pi) | 13 | GPIO4_A0 | parameter `rst_pin` |
| LCD DC (BCM 25) | 22 | GPIO4_A4 | parameter `dc_pin` |
| LCD backlight (BCM 18) | 12 | GPIO3_C7 | parameter `bl_pin` |
| E-stop input (BCM 5), only for the GPIO battery monitor | 29 | GPIO4_A5 | `battery_voltage_checking.py`, parameter `estop_pin` |
| Battery level bits (BCM 6, 13, 19), only for the GPIO battery monitor | 31, 33, 35 | GPIO3_D4, GPIO3_D7, GPIO3_D0 | `battery_voltage_checking.py`, parameter `battery_pins` |
| Arduino Nano serial | USB cable | `/dev/ttyUSB0` (default) or `/dev/ttyACM0` | `arduino_bridge`, parameter `serial_port` |

Notes:
- The Raspberry Pi pins 8 and 10 (`/dev/ttyS0` in the ROS 1 version) are the **debug console UART2** on this baseboard and must not be used for the Nano. The Nano is connected with its USB cable. (A wired link would use UART7 on header pins 15 and 16 through the logic level converter, for example `serial_port:=/dev/ttyS7`.) Do not power the Nano from USB and from the Dingo PCB at the same time.
- The GPIO battery monitor is an alternative to the voltage measurement of the Nano and is not started by `dingo.launch.py`.

### 4.2 Check and enable the interfaces
Look at what the OS image provides:
```bash
sudo i2cdetect -l          # list of I2C buses, I2C2 is normally /dev/i2c-2
ls /dev/spidev*            # should list /dev/spidev3.0 (SPI3)
gpiodetect                 # should list gpiochip0 ... gpiochip4, labelled gpio0 ... gpio4
ls /dev/gpiochip*
```
If I2C2 or SPI3 are missing, enable them in the device tree of your OS image (overlay settings in the boot configuration or the configuration tool of the image; how it is done depends on the image, so follow the documentation of the image). Reboot and check again.

`gpiodetect` must list `gpiochip0` to `gpiochip4`: Adafruit Blinka opens them while it is imported. If your image names the chips differently, the servo board and the IMU cannot be used.

### 4.3 Permissions
To run ROS as a normal user the device files need the right group:
```bash
sudo groupadd ros
sudo adduser $USER ros
sudo tee /etc/udev/rules.d/99-ROS.rules > /dev/null <<'EOF'
KERNEL=="ttyUSB[0-9]*", OWNER="root", GROUP="ros", MODE="0660"
KERNEL=="ttyACM[0-9]*", OWNER="root", GROUP="ros", MODE="0660"
KERNEL=="spidev3.*", OWNER="root", GROUP="ros", MODE="0660"
KERNEL=="i2c-[0-9]*", OWNER="root", GROUP="ros", MODE="0660"
KERNEL=="gpiochip[0-9]*", OWNER="root", GROUP="ros", MODE="0660"
EOF
sudo usermod -aG dialout $USER
sudo udevadm control --reload-rules && sudo udevadm trigger
```
Log out and in again (or reboot) so that the groups apply, then check with `groups`.

### 4.4 Tell Adafruit Blinka which board this is
Blinka (used for the servo board and the IMU) does not know the ELTAY RM66, and without help `import board` finds no pins. Use the board `ORANGE_PI_3B`: its 40-pin map is identical to the baseboard (all 28 GPIO pins were compared with the baseboard pinout) and its default I2C bus is I2C2.
```bash
echo "export BLINKA_FORCEBOARD=ORANGE_PI_3B BLINKA_FORCECHIP=RK3566" >> ~/.bashrc
source ~/.bashrc
```
`ros2 launch dingo dingo.launch.py` and the Docker image set these two variables themselves; you need them in your shell for scripts that you start by hand (for example the servo calibration).

### 4.5 I2C devices
```bash
sudo i2cdetect -y 2
```
The PCA9685 servo board should answer at address 0x40 and the BNO055 IMU at 0x28 or 0x29. If the matrix is empty, check the wiring, the power of the servo board and the bus number (4.2). If it only works with `sudo`, the permissions (4.3) are not applied yet.

### 4.6 Arduino Nano
The Nano measures the battery voltage and the servo voltage and detects the e-stop (the servo voltage drops when it is pressed). It sends one text line per second, and one at once when the e-stop changes, over its USB serial port. rosserial and micro-ROS are not used (rosserial does not exist for ROS 2 and micro-ROS does not fit an ATmega328).

1. On any computer install the [Arduino IDE](https://www.arduino.cc/en/software), open `dingo_nano/dingo_arduino.ino` (the sketch needs no extra libraries), choose the board **Arduino Nano** (try *ATmega328P (Old Bootloader)* if the upload fails) and the port, and upload.
2. Open the Serial Monitor at **57600 baud**. About 15 seconds after power-up (the sketch waits that long) it prints lines like
   `$DINGO,0,16.42,7.03*62`
   which are `$DINGO,<e-stop 0|1>,<battery volts>,<servo buck volts>*<checksum>`. A line starting with `#` is a message of the Nano.
3. Connect the Nano to the robot computer and find the port:
```bash
ls /dev/ttyUSB* /dev/ttyACM*     # unplug and plug the cable to see which one appears
python3 -m serial.tools.miniterm /dev/ttyUSB0 57600     # Ctrl+] to leave
```
Opening a USB serial port resets the Nano, so after every start of the bridge the first data appears after about 15 seconds.

### 4.7 LCD
The LCD node follows the [Waveshare tutorial for the 1.47 inch LCD module](https://www.waveshare.com/wiki/1.47inch_LCD_Module). It needs the fonts of the Waveshare example code in the system font folder:
```bash
cd ~
sudo apt install -y unzip wget
wget https://files.waveshare.com/upload/8/8d/LCD_Module_RPI_code.zip
unzip ./LCD_Module_RPI_code.zip
cd ~/LCD_Module_RPI_code/RaspberryPi/python/Font
sudo cp Font00.ttf Font01.ttf Font02.ttf /usr/share/fonts/truetype/
```
(The zip is the vendor's code for a Raspberry Pi, only its font files are used.) The LCD backlight is switched on or off, its brightness cannot be changed because libgpiod has no PWM.

### 4.8 Gamepad (Bluetooth)
The module has its own Bluetooth. Install and pair (example with a PS4 controller):
```bash
sudo apt install -y bluetooth bluez bluez-tools joystick
sudo systemctl enable --now bluetooth
bluetoothctl
```
Inside `bluetoothctl`: `power on`, `agent on`, `default-agent`, `scan on`, put the controller into pairing mode (PS4: hold Share and PS buttons), then `pair AA:BB:CC:11:22:33`, `trust AA:BB:CC:11:22:33`, `connect AA:BB:CC:11:22:33` (use your controller's address), `exit`.

Test the controller:
```bash
ros2 run joy joy_enumerate_devices        # the controller must be listed
ros2 run joy joy_node &                   # start the joy node
ros2 topic echo /joy                      # move the sticks and press buttons, the numbers must change
```
At this stage the controller only connects after you run `bluetoothctl`. To make it reconnect by itself, follow 11.2.

The axis and button order in `/joy` depends on the node and on the controller. The code knows two layouts, selected with the launch argument `joy_layout`:
- `legacy` (default): the order of the ROS 1 `joy_node` with a PS4 controller (R1 = button 5, L1 = button 4, X = button 0, d-pad on axes 6 and 7);
- `game_controller`: the standard SDL order of `game_controller_node` (d-pad on buttons 11 to 14). Use it together with `joy_executable:=game_controller_node`.

Check with `ros2 topic echo /joy` that your pad produces what the chosen layout expects. If the robot walks in the wrong direction, the signs of the axes of your pad differ and the layout table `JOY_LAYOUTS` in `dingo_input_interfacing/HardwareConfig.py` needs a change.

### 4.9 Servo calibration
- View the CalibrateServos script itself for additional instructions on dialing in servos: `dingo_hardware_interfacing/dingo_servo_interfacing/src/dingo_servo_interfacing/CalibrateServos.py`
- Example commands (run from the folder of the script, with the Blinka variables from 4.4 exported):
```bash
cd ~/DingoQuadruped/dingo_ws/src/dingo_hardware_interfacing/dingo_servo_interfacing/src/dingo_servo_interfacing
python3 CalibrateServos.py all cal      # move all servos to the calibration position
python3 CalibrateServos.py fr high      # move the front right servo to the high position
```
Keep the robot on a stand while you calibrate.

## 5. Check that everything works
Do these in order, each step needs the previous one. Steps 1 and 2 need no hardware.

1. **Driver without hardware** (robot not needed, only the build):
```bash
ros2 launch dingo dingo.launch.py is_physical:=false use_joystick:=false
```
   In a second terminal: `ros2 node list` shows `/dingo`, and `ros2 topic hz /joint_space_goals` shows about 50 Hz.
2. **Joystick**: stop the launch, start it again with `is_physical:=false` (joystick enabled) and press R1 on the gamepad. The log prints `State changed from BehaviorState.REST to BehaviorState.TROT`.
3. **Nano**: `ros2 run dingo_peripheral_interfacing arduino_bridge --ros-args -p serial_port:=/dev/ttyUSB0`, wait about 15 seconds, then `ros2 topic echo /electrical_measurements` shows the battery voltage, and `ros2 topic echo /emergency_stop_status` shows `false` (`true` while the e-stop is pressed).
4. **Servo board and IMU**: `sudo i2cdetect -y 2` (section 4.5). To test the code path with the real hardware, run the driver with the robot on a stand, see section 6.

## 6. Run the robot
**Put the robot on a stand with the legs in the air for the first run, and keep the e-stop within reach.**

```bash
ros2 launch dingo dingo.launch.py
```
The driver should be started before any other code is launched on the Dingo. It starts joystick control of the robot and allows joint and task space commands to be received from other code or controllers via command topics.

Arguments (booleans are `true`/`false`, the ROS 1 version used `1`/`0`):
- `is_physical` (true/false): Is the code being run on the Dingo itself? Default: `true`
- `is_sim` (true/false): Should the code publish joint values to the simulator? Default: `false`
- `use_joystick` (true/false): Is a joystick being used for control? Default: `true`
- `use_keyboard` (true/false): Is the keyboard being used for control? Default: `false`
- `serial_port` (name of port): The serial port of the Arduino Nano, read by the `arduino_bridge` node. Default: `/dev/ttyUSB0`
- `use_imu` (true/false): Should IMU data be used to correct the robot's joint angles? Default: `false`
- `joy_layout` (`legacy`/`game_controller`) and `joy_executable` (`joy_node`/`game_controller_node`): see 4.8. Defaults: `legacy`, `joy_node`

With no arguments it assumes a joystick is used and launches the hardware interface with IMU feedback disabled. For example, with the Nano on `/dev/ttyACM0` and the IMU on:
```bash
ros2 launch dingo dingo.launch.py serial_port:=/dev/ttyACM0 use_imu:=true
```
The launch also starts the Arduino bridge and the LCD node when `is_physical` is true.

### Joystick controls
<p align="center">
    <img src="assets/joystick control map.jpg" style="align:centre" width="50%">
</p>

The diagram above shows the mapping of joystick commands for the Dingo. These instructions are based on a PS4 type controller. An alternative, more general description of joystick commands is below:

The Dingo has two main states: Rest and Trot.
- While in the TROT state: Left stick controls the robot's movement. Right stick controls the robot's tilt and turning.
- While in the REST state: Left stick is disabled. Right stick controls the robot's gaze while staying in place.

Buttons:
- Joystick Control Toggle (L1 Button): Pause/Resume control from the joystick (switches between manual and external control).
- Gait Toggle (R1 Button): Toggles between trotting and resting modes.
- Hop Request (X button): Perform a hop (Currently not implemented).

Movement: (Speed proportional to how far stick is moved)
- Left Stick (Horizontal): Pushing left or right strafes the robot in that direction.
- Left Stick (Vertical): Push up to move forward, down to move backward.

Gaze:
- Right Stick (Horizontal): Pushing left or right turns the robot in that direction.
- Right Stick (Vertical): Push up to raise front of robot, down to raise back of robot.

Orientation:
- D-pad (Vertical): Pressing up or down adjusts the height of the robot.
- D-pad (Horizontal): Pressing left or right tilts the robot in that direction.

### Keyboard
`ros2 launch dingo dingo.launch.py use_keyboard:=true use_joystick:=false` starts the keyboard node. It reads `/dev/input/event0` by default; give another device with `ros2 run dingo_input_interfacing Keyboard.py --ros-args -p keyboard_device:=/dev/input/event3`. Keys: W/S forward and back, A/D strafe, arrow keys tilt and turn, 1 = R1, 2 = X, Backspace = L1, 7/8 and 9/0 = d-pad, Shift = faster.

### Look at what the controller does
```bash
ros2 topic echo /task_space_goals
ros2 topic echo /joint_space_goals
```
(joint angles are published in degrees).

## 7. Simulation
Needs a machine with Gazebo and rviz, so a development machine (section 8 if it is not Ubuntu 22.04). Install the extra packages first:
```bash
sudo apt install -y ros-humble-desktop ros-humble-xacro ros-humble-robot-state-publisher ros-humble-joint-state-publisher-gui ros-humble-gazebo-ros-pkgs ros-humble-gazebo-ros2-control ros-humble-ros2-control ros-humble-ros2-controllers
```
Start Gazebo (add `gui:=false` to run without a window, `verbose:=true` for more log output):
```bash
ros2 launch dingo_gazebo simulation.launch.py
```
and in another terminal the driver in simulation mode:
```bash
ros2 launch dingo dingo.launch.py is_physical:=false is_sim:=true
```
The driver sends all 12 joint angles (radians, order FR, FL, RR, RL legs, each theta1, theta2, theta3) as one `std_msgs/Float64MultiArray` to `/joint_group_position_controller/commands`. The simulated joints are commanded by position through `ros2_control` (see `dingo_gazebo/config/controllers.yaml`), the PID effort controllers of the ROS 1 version are gone. The simulated IMU is published on `/notspot_imu/base_link_orientation`.

To look at the robot model only: `ros2 launch dingo_description dingo_rviz.launch.py`.

Note for editing `dingo_description/urdf/dingo.urdf`: do not write a colon followed by a space inside XML comments. `gazebo_ros2_control` passes the whole file to the controller manager as a YAML parameter value and such a sequence breaks the parsing.

## 8. Development in Docker (for example on Ubuntu 24.04)
ROS 2 Humble can only be installed natively on Ubuntu 22.04. On any other system (for example 24.04) use the Docker image, which is Ubuntu 22.04 with ROS 2 Humble, Gazebo and rviz. It is also what the code was tested in.

```bash
sudo apt install -y docker.io docker-compose-v2      # skip if Docker is already installed (docs.docker.com)
sudo usermod -aG docker $USER                         # log out and in again afterwards
cd ~/DingoQuadruped
xhost +local:docker                                   # lets rviz2 and Gazebo open windows, once per login
docker compose -f Docker-compose.yaml build           # the first build takes 10-20 minutes
docker compose -f Docker-compose.yaml up -d
docker compose -f Docker-compose.yaml exec dingoquadruped bash
```
The compose file is named `Docker-compose.yaml` (capital D), so docker has to be told its name with `-f`. Inside the container:
```bash
cd /dingo_ws
rosdep update
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash
```
The folder `dingo_ws` is mounted into the container, so files edited on your computer appear in the container and the other way round. The image sets `BLINKA_FORCEBOARD` and `BLINKA_FORCECHIP` for the RM66. Folders `build`, `install` and `log` created in the container belong to root; if you cannot delete them natively use `sudo chown -R $USER:$USER dingo_ws`.

To stop the container: `docker compose -f Docker-compose.yaml down`. Rebuild the image after the `Dockerfile` changes.

### Visual Studio Code
The files in the base directory also allow the code to be inspected and debugged in the container from vscode: install Docker and vscode, add the extensions *C/C++ Extension Pack*, *Docker*, *Dev Containers* and *ROS*, open the base folder with `code .` and choose "build" or "run" when asked. When the container is built, "ROS2.humble" should appear in the bottom left corner. To debug a node, use the ROS extension: attach to a running node (`ros2 run package_name node_name`) or debug from a launch file. If the debugger does not stop at breakpoints, build with `--cmake-args -DCMAKE_BUILD_TYPE=Debug`.

## 9. Troubleshooting

| What you see | What to do |
|---|---|
| `ros2: command not found` | `source /opt/ros/humble/setup.bash` (3.2) and `source ~/DingoQuadruped/dingo_ws/install/setup.bash` |
| `Package 'dingo' not found` | the workspace is not built or not loaded: `cd ~/DingoQuadruped/dingo_ws && colcon build --symlink-install && source install/setup.bash` |
| `E: Unable to locate package ros-humble-...` | the ROS repository is not added or the system is not Ubuntu 22.04: check `lsb_release -d` and step 3.2 |
| `AttributeError: module 'board' has no attribute 'D29'` or similar | Blinka does not know the board: `export BLINKA_FORCEBOARD=ORANGE_PI_3B BLINKA_FORCECHIP=RK3566` (4.4) |
| `FileNotFoundError` while importing `board`, or `libgpiod Python bindings not found` | `/dev/gpiochip0` to `gpiochip4` do not exist (4.2), or `python3-libgpiod` is not installed (3.3) |
| `Permission denied` for `/dev/i2c-2`, `/dev/spidev3.0`, `/dev/ttyUSB0`, `/dev/gpiochip*` | permissions (4.3); check `groups` and log out and in |
| `i2cdetect` shows nothing | wrong bus number, I2C2 not enabled in the device tree (4.2), wiring, or the servo board has no power |
| `Cannot open /dev/ttyUSB0` in the log of `arduino_bridge` | the Nano has another name (`ls /dev/ttyUSB* /dev/ttyACM*`, pass it with `serial_port:=`), no permission (4.3), or the cable is a charge-only cable |
| `/electrical_measurements` stays silent | wait 15 seconds after the port is opened (the Nano restarts); check the Nano with the Serial Monitor at 57600 baud (4.6) |
| `Ignoring a corrupted line from the Arduino` | wrong baud rate (must be 57600) or a noisy link; sketch and bridge must be the ROS 2 versions |
| LCD node: `OSError: cannot open resource` | the Waveshare fonts are missing (4.7) |
| LCD node: SPI or GPIO error | `/dev/spidev3.0` missing (4.2) or no permission (4.3); check the pins (4.1) |
| `Joy message has ... buttons and ... axes but layout ... needs at least ...` | the pad has fewer inputs than the chosen `joy_layout`; see 4.8 |
| Robot does not react to the gamepad | `ros2 topic echo /joy` shows nothing: pair the pad again (4.8); shows numbers: wrong layout (4.8) or the robot is e-stopped (`ros2 topic echo /emergency_stop_status`); press L1 once if it is in external mode (the log says which mode it is in) |
| Robot is stuck in e-stop | `/emergency_stop_status` is true: release the e-stop; the state is repeated every second |
| Gazebo hangs at start, `Getting models from http://models.gazebosim.org` in the log | Gazebo cannot find a model; start it with `ros2 launch dingo_gazebo simulation.launch.py` (it sets the model path) and make sure the workspace is built and loaded |
| Docker: `no configuration file provided: not found` | add `-f Docker-compose.yaml` (8) |
| Docker: windows do not open | run `xhost +local:docker` on the host (8) |

## 10. Differences from the ROS 1 version

| ROS 1 (Noetic, Ubuntu 20.04, Raspberry Pi) | ROS 2 (Humble, Ubuntu 22.04, RM66) |
|---|---|
| `catkin build`, `source devel/setup.bash` | `colcon build --symlink-install`, `source install/setup.bash` |
| `roslaunch dingo dingo.launch is_sim:=1` | `ros2 launch dingo dingo.launch.py is_sim:=true` (booleans are `true`/`false`) |
| `rosrun`, `rostopic echo` | `ros2 run`, `ros2 topic echo` |
| messages in `dingo_control` and `dingo_peripheral_interfacing` | one package `dingo_msgs`; fields of `JointSpace` and `TaskSpace` are lower case (`fl_foot`, ...), there is no `seq` |
| rosserial and the Nano sketch with `ros.h` | text frames over USB serial and the `arduino_bridge` node |
| `RPi.GPIO`, Raspberry Pi pin numbers | libgpiod, pins by name (`GPIO4_A5`), configured with launch parameters |
| `/dev/ttyS0` for the Nano | USB serial `/dev/ttyUSB0` |
| the driver had blocking loops | one 50 Hz timer, modes manual / external / e-stopped |
| `joy` axis order fixed in the code | layout chosen with `joy_layout` |
| Gazebo with PID effort controllers per joint | Gazebo Classic with `ros2_control`, one position controller for all 12 joints |

## 11. Extra setup notes

### 11.1 Wi-Fi
If your image uses netplan (the Ubuntu server images do), edit the file in `/etc/netplan/` (for example `50-cloud-init.yaml`) and add the following to the bottom of the file, then run `sudo netplan apply`:
```.
    wifis:
        wlan0:
            optional: true
            dhcp4: true
            access-points:
                "<wifi SSID>":
                    password: "<wifi password>"
```
The Wi-Fi of the module is provided by the module itself. The name of the interface may differ from `wlan0` (`ip link`). Images with a desktop use NetworkManager (`nmtui`).

### 11.2 Make the gamepad reconnect by itself
At the end of 4.8 the controller connects only if you run `bluetoothctl` and press the pair button. To bypass that:
- Create a shell script called `connect_controller.sh` (make a note of where you create it) with the following contents:
```.
#!/bin/bash

# Replace 'XX:XX:XX:XX:XX:XX' with your controller's MAC address
controller_mac="XX:XX:XX:XX:XX:XX"

# Use bluetoothctl to connect the controller
bluetoothctl <<EOF
connect $controller_mac
exit
EOF
```
- Make it executable by running `chmod +x connect_controller.sh`
- Create a udev rule (for example in `/etc/udev/rules.d/99-controller.rules`) to run this script every time the controller attempts to pair: `SUBSYSTEM=="bluetooth", KERNEL=="hci0", ACTION=="add", ENV{DEVTYPE}=="adapter", TAG+="systemd", SYMLINK+="bluetooth", RUN+="/bin/sleep 10", RUN+="/path/to/connect_controller.sh"`
- reload the udev rules: `sudo udevadm control --reload`

The controller should now autopair every time the pair button is pressed, without needing to do anything on the robot.

### 11.3 Bluetooth audio (XYAP15H / RADIOTEHN amplifier)
If you connect to the robot over SSH and want audio output to a Bluetooth amplifier (XYAP15H, shown as `RADIOTEHN`), install the required stack first:

- `sudo apt-get update`
- `sudo apt-get install -y bluetooth bluez bluez-tools pulseaudio pulseaudio-module-bluetooth alsa-utils`
- Optional (GUI mixer for desktop sessions): `sudo apt-get install -y pavucontrol`

Start/enable Bluetooth and make sure PulseAudio is running for your SSH user session:

- `sudo systemctl enable --now bluetooth`
- `pulseaudio -k || true` (stop old instance if it exists)
- `pulseaudio --start`

Pair/connect `RADIOTEHN` (this amplifier usually exposes **two Bluetooth MAC addresses**; one may refuse audio profile, so try both):

1. `bluetoothctl`
2. Inside `bluetoothctl`:
   - `power on`
   - `agent on`
   - `default-agent`
   - `scan on` (wait until you see one or two `RADIOTEHN` entries with different MAC addresses)
   - `pair XX:XX:XX:XX:XX:XX`
   - `trust XX:XX:XX:XX:XX:XX`
   - `connect XX:XX:XX:XX:XX:XX`
   - `info XX:XX:XX:XX:XX:XX` (check that audio UUIDs/profiles are present)
3. If connect fails or no audio profile appears, repeat pair/connect with the second `RADIOTEHN` MAC.

Select the Bluetooth sink for playback:

- `pactl list short sinks`
- `pactl set-default-sink <bluetooth_sink_name>`
- Optional GUI (if desktop/session available): `pavucontrol`

Quick audio checks:

- `speaker-test -c 2 -t wav`
- `aplay -l`

Common SSH + Bluetooth/PulseAudio issues and fixes:

- `Failed to connect: org.bluez.Error.Failed br-connection-profile-unavailable` (exact BlueZ error text)
  - Usually wrong MAC/profile. Disconnect and connect the other `RADIOTEHN` address.
- `pa_pid_file_create() failed` or PulseAudio does not start
  - Kill stale process/runtime state and restart:
    - `pulseaudio -k || true`
    - `rm -rf /run/user/$(id -u)/pulse 2>/dev/null || true`
    - `pulseaudio --start`
- `No default controller available`
  - Bluetooth service is down:
    - `sudo systemctl restart bluetooth`
    - `rfkill list`
    - `sudo rfkill unblock bluetooth`
- Device pairs but no sound output
  - Set sink explicitly with `pactl set-default-sink ...` and verify in `pavucontrol`/`pactl list short sinks`.
- `Connection refused` / `Not available` during SSH sessions
  - Ensure commands are run under the same user that owns the audio session, then restart PulseAudio and reconnect.

### 11.4 Backup of the system storage
It's a good idea to back up the storage every so often. If the robot boots from an SD card:
- Take out the card from the baseboard and mount it into another linux system.
- Run these commands to backup/restore. Replace source/destination appropriately (check the device name with `lsblk` first, a wrong name destroys data).
    - Backup to file: `sudo dd if=/dev/sdb of=~/dingo_backup.img bs=4M status=progress`
    - Restore back to the card: `sudo dd if=~/dingo_backup.img of=/dev/sdb bs=4M status=progress`

If it boots from the eMMC of the module, use the tools of the vendor.
